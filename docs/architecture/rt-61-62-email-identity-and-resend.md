### 3.1 DNS records Resend will require

Exact values are generated by the Resend account and **are not knowable from here**: the DKIM public key is account-specific, so no placeholder values are given. Typical record **shape** with Resend's default setup (confirm every host and value in the dashboard):

| Type | Host (as entered at HostGator) | Value | Priority |
| --- | --- | --- | --- |
| TXT | `resend._domainkey` | the `p=...` DKIM public key shown by Resend | n/a |
| MX | `send` | the feedback server shown by Resend (an `amazonses.com` host for the chosen region) | as shown (typically 10) |
| TXT | `send` | SPF for the `send` subdomain as shown by Resend (typically `v=spf1 include:amazonses.com ~all`) | n/a |

HostGator zone-editor note: some panels want only the subdomain part (`send`), others the full name (`send.ricardotour.com`). Add one record at a time and check the resulting name.

### 3.2 Titan coexistence

- With the default Resend setup, SPF and MX go on the **`send` subdomain**, not the apex. The apex SPF `v=spf1 include:spf.titan.email ~all` therefore **does not need to change**, and the apex MX stay Titan's. No merged SPF record is required for this setup.
- Do **not** add a second SPF record at the apex (two SPF records at one name break SPF).
- Do not edit the Titan MX, SPF or the `default._domainkey` DKIM records.
- If the Resend dashboard ever asks for an apex SPF change, stop. The safe merged record would be `v=spf1 include:spf.titan.email include:amazonses.com ~all` as **one** record, applied only after the Owner confirms. It is not needed for the default setup.
- DKIM selectors differ (`default` for Titan, `resend` for Resend), so they coexist.

### 3.3 Optional, not required: DMARC

No DMARC exists. It is a future improvement and not a blocker. When the Owner wants it, a safe starter is a TXT at `_dmarc` with `v=DMARC1; p=none; rua=mailto:contato@ricardotour.com`, which monitors without affecting delivery. Not added here.
