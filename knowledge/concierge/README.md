# AI Concierge V1 knowledge registry

This directory began as the machine-readable RT-68 governance contract. [The RT-68 source contract](../../docs/architecture/rt-68-concierge-knowledge-source-contract.md) records the initial allowlist; RT-93's later Owner-approved editorial files extend the candidate inventory under [RT-69 Stage 1](../../docs/architecture/rt-69-concierge-ingestion-process.md). `manifest.json` declares the source classes and individual immutable-content versions; `manifest.schema.json` constrains those records. Registration does not ingest or publish content to OpenAI.

`source_classes` are registration rules, **not knowledge records**. Stage 1.5 binds the Owner directive in RT-69 Jira comment 13290 to five exact factual PT editorial digests and refreshes the four public-gate catalog projections. All nine registered versions are now locally `ACTIVE` with `approved_for_rag: true`; the recommendation policy remains runtime behavior and is excluded from `sources`. Checked-in institutional/About UI content remains `BLOCKED` until its Rick Travel wording is reconciled. Local activation does **not** upload, index, or expose the sources through production Concierge. The `source_sha256` and `normalized_sha256` digests identify exact source and immutable local snapshots; catalog snapshots contain only PT title, published prose, public URL, and provenance.

`drafts/` is the authoring and review space; `approved/` holds only Owner-approved canonical content organized by locale and subject; `archive/` holds retired content. Placement in `approved/` does not make a document RAG-eligible. Only a manifest source version with `status == ACTIVE` **and** `approved_for_rag == true` can pass the retrieval eligibility gate.

A future source version is retrieval-eligible only when `status == ACTIVE` **and** `approved_for_rag == true`, and it still passes the exact RT-68 canonical-path, locale, publication, field, and freshness checks. `ACTIVE` alone is insufficient; a class declaration never grants retrieval eligibility. DRAFT, BLOCKED, and RETIRED versions must never be retrieved. The schema prevents non-ACTIVE versions from setting `approved_for_rag: true` and requires approval metadata for eligible versions.

The RT-69 lifecycle is **CANONICAL → VALIDATE → NORMALIZE → VERSION → CHUNK/INDEX → PUBLISH → RETIRE/ROLLBACK**. Stage 1.5 stops after local activation. Stage 2 must reverify approval evidence, current catalog publication and canonical digests before hosted ingestion or production retrieval. A source change or withdrawal retires the old version before asynchronous index removal. Rollback requires fresh verification that the exact canonical version is still published, approved, and eligible; it never silently reactivates withdrawn content.

No tour price, availability, schedule/capacity, private data, unsupported safety fact, legacy Rick Travel claim, or unapproved institutional/About copy belongs in Concierge RAG. Price questions go to the current product/booking page or human handoff. The operational Oner widget is a separate commercial flow: Oner inventory, flights, hotels, packages, provider prices, and provider availability are not Concierge sources. No open-web source is enabled.

The manifest uses Draft-07 JSON Schema with explicit Ajv validation in `npm run check:concierge-sources`. Re-running `node scripts/rt-69-registry.mjs register` is idempotent for unchanged sources, never overwrites an immutable snapshot, and retires a prior version before registering changed content. `npm run snapshot:concierge-catalog` reads the configured public gate, writes only new immutable PT projections, and updates the mutable local `catalog-current.json` pointer with an observation timestamp; it does not publish them. `approval-stage-1-5.json` binds exact digests and evidence; `node scripts/rt-69-activate-local.mjs` performs an all-or-nothing local manifest transition only while the catalog observation is fresh. No production runtime reads this registry yet. All class rules have `approved_for_rag: false`; only validated individual versions can be locally active.
